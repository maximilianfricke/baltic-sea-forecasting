# Partition strategy comparison (job 4467)

Do partitions that a cost model rates differently from the `message-passing`
branch's geographic split actually train faster or use less memory? This
compares four ways of assigning the 1-degree `global_cluster_graph` to GPUs,
with predictions written before the run.

## Setup

| Setting | Value |
| --- | --- |
| Code | `lassi-partition-benchmark` at `2539d36`: `message-passing` at `390f480` plus `--partition-strategy file` |
| Job | `jobs/partition_comparison.sbatch`, one 4-GPU allocation (`studgpu-node02`, GTX 1080 Ti), 48 min |
| Model | GraphEFM, hidden 64 and 256, 2 processor layers, batch 2, FP32, **one AR step**, no checkpointing |
| Data | 1-degree sample data, `rank-zero-broadcast` for every strategy (rank-local shards exist only for the geographic split) |
| Timing | 5 warm-up + 25 measured steps per run, two repetitions, medians averaged |
| Model step | critical path of forward, backward, gradient sync, metric reduce and optimizer |
| Peak | largest peak allocated over the GPUs |

Strategies (owner files in [`partitions/`](partitions), generated by
[`benchmarks/partition_candidates`](../../benchmarks/partition_candidates)):

| Name | What it is | Files (sha256 prefix) |
| --- | --- | --- |
| geographic | the branch's built-in per-layer lat/lon RCB, balanced by node count per layer | built in |
| lon_bands | longitude strips shared by all layers, balanced by measured memory weight | `f25f9bcd…` (k2), `e864f8e8…` (k4) |
| mtkahypar_km1 | Mt-KaHyPar 1.7.1, hypergraph with one net per (sender, edge set) weighted by exchanges per step, so the connectivity objective equals halo traffic; memory-weight balance, ε = 0.03 | `c0472cae…`, `64d0c73b…` |
| metis | METIS 5.1 (pymetis 2025.2.2), ufactor 10, edge weights = exchanges. **Intended:** one balance constraint per layer. **Actual:** pymetis uses one weight per node and silently reads only the first n entries of the weight array, so this partition is balanced on unintended single weights (found 2026-11-25; see below) | `542fa98f…`, `109c2096…` |

Every file was loaded through `build_partition_from_graph_efm` on the real
model before the run; the resulting halo counts per GPU and relation equal

also reproduces the halo counts recorded by jobs 4311/4312.

## Predictions (written before the run)

1. Peak memory differences between strategies follow the busiest GPU's memory share.
2. Hidden 64: all model steps within ±5% of geographic (noise).
3. Hidden 256: Mt-KaHyPar +3% / +5% and METIS +4% / +8% slower at k = 2 / 4; lon_bands ≈ 1% faster.
4. One GPU at hidden 256 runs out of memory.
5. 2 → 4 GPU model step: 1.0–1.1× at hidden 64, 1.6–1.8× at hidden 256.

## Conclusion

At hidden 256 both graph partitioners are 3–5% slower than the geographic
split despite 3.7–5.9× less halo traffic: the slowest GPU's work per
synchronised operation decides the step time, not halo volume. lon_bands is
marginally better than geographic on every measure and can replace it
directly.

## Caveats

- **The METIS partition is not a multi-constraint partition.** pymetis's
  `part_graph` takes one weight per node; given 3n weights it uses the first
  n (checked: identical result with the array cut to n entries). The METIS
  rows measure a valid METIS partition, and the cost-model predictions were
  computed from that exact file, so the measured-vs-predicted comparison
  stands. What they don't show is how multi-constraint METIS performs; that
  needs a direct `METIS_PartGraphKway` call with `ncon > 1`, as on
  `nils-pnemo` (the Windows pymetis build does not export it).

- AR1 and rank-zero broadcast, unlike the AR4 rank-local runs on
  `message-passing`. Broadcast adds a replicated full-grid part (≈ +0.4 GiB at
  hidden 64 against the rank-local runs); differences between strategies are
  unaffected.
- One node, two repetitions; hidden-64 differences are within run-to-run
  spread.
- The cost model is in [`neural_lam/graph_viewer`](https://github.com/maximilianfricke/baltic-sea-forecasting/tree/lassi-balance-metrics/neural_lam/graph_viewer)
  on `lassi-balance-metrics`.

## Hidden-size sweep (model step, ms, two repetitions)

| Hidden | 1 GPU | 2 GPUs | 4 GPUs | 2 → 4 GPUs | Peak per GPU (1 / 2 / 4) |
| ---: | ---: | ---: | ---: | ---: | --- |
| 64 | 220 | 144 | 121 | 1.19× | 3.55 / 2.09 / 1.38 GiB |
| 128 | 360 | 222 | 149 | 1.49× | 6.85 / 4.00 / 2.55 GiB |
| 192 | — | 321 | 203 | 1.58× | — / 5.90 / 3.72 GiB |
| 256 | — | 427 | 263 | 1.63× | — / 7.82 / 4.93 GiB |

- The 2 → 4 GPU speedup grows with hidden size; 4 GPUs are faster than 2 at
  every size measured.
- **Doubling GPUs and hidden size together** (1 GPU h64 → 2 GPUs h128 → 4 GPUs
  h256): 220 → 222 → 263 ms with 3.55 → 4.00 → 4.93 GiB per GPU. Compute per
  GPU doubles each step, but the time barely moves: at these sizes the GPUs
  are limited by kernel launches and synchronisation, not arithmetic.
- **Run-to-run variability at hidden 64 on 4 GPUs:** 121 ms here vs 188.5 ms
  in job 4467 (same node, same code); forward, backward, metric reduction and
  optimizer phases were all slower in 4467. All 2-GPU and hidden-256 runs
  agree within 1–3% between the jobs. Small, launch-bound configurations are
  sensitive to CPU contention on the node; compare them only within one job.

# Inference memory (job 5932)

One `predict_step` (prior, sample, decoder) under `no_grad`, batch 1, one
GTX 1080 Ti, after a warm-up step ([`benchmarks/inference_memory.py`](../../benchmarks/inference_memory.py),
[`jobs/inference_memory.sbatch`](../../jobs/inference_memory.sbatch);
results in [`5932/`](5932)). Predicted from a CPU measurement at 1° (a
dispatch-mode tracker of live tensor bytes), scaled by the 0.25° graph's
edge and node counts.

| Graph | Hidden | Predicted | Peak allocated | Step |
| --- | ---: | ---: | ---: | ---: |
| 1° | 64 | 0.331 GiB activations | 0.332 GiB activations (0.38 GiB total) | 54 ms |
| 1° | 256 | 1.320 GiB activations | 1.324 GiB activations (1.44 GiB total) | 143 ms |
| 0.25° | 64 | ≈ 5.5 GiB | 5.24 GiB | 587 ms |
| 0.25° | 96 | ≈ 8.2 GiB | 7.90 GiB | 623 ms |
| 0.25° | 112 | ≈ 9.5 GiB | 9.40 GiB | 735 ms |
| 0.25° | 128 / 192 / 256 | out of memory | out of memory | — |

- The peak is the edge MLP of the largest edge sets: at 1° the layer norm over
  all 126,107 m2g edges; at 0.25°, hidden 256 the run fails allocating the
  3.34 GiB g2m edge input (1.17 M edges × 3 × 256 values).
- Inference needs ≈ 5× less memory than a training step, but at 0.25° one
  11 GB GPU still fits only hidden ≈ 112–127 without changes. Processing edges
  in chunks (no state is kept between chunks without gradients) removes most
  of the peak; graph splitting would also, but needs several GPUs per member.

# Edge-chunked vs split inference (job 5956)

0.25° `global_cluster_analysis`, batch 1, one 4-GPU allocation on
`studgpu-node02`, 14 min ([`jobs/inference_chunking_vs_split.sbatch`](../../jobs/inference_chunking_vs_split.sbatch),
branch `lassi-inference-chunking`; results in [`5956/`](5956)).

- **Chunked:** `utils.inference_chunking(65536)` on one GPU: row-wise MLPs in
  row chunks, message passing in edge chunks added into the receiver
  aggregate (gradients off). Forecast equal to unchunked (max |diff| 1.9e-6).
- **Split:** `benchmarks/inference_split.py`, the sharded prior and decoder of
  the model-parallel core, each rank embedding only its own nodes and edges;
  equal to the unsplit forecast on CPU (≈ 1e-6). No chunking.

| Hidden | Unchunked, 1 GPU (5932) | Chunked, 1 GPU | Split, 2 GPUs | Split, 4 GPUs |
| ---: | --- | --- | --- | --- |
| 64 | 587 ms, 5.24 GiB | 615 ms, 2.55 GiB | 302–307 ms, 2.97 GiB | 171–176 ms, 1.75 GiB |
| 112 | 735 ms, 9.40 GiB | 720 ms, 4.05 GiB | 353–375 ms, 4.73 GiB | 220–234 ms, 2.63 GiB |
| 128 | out of memory | 739 ms, 4.56 GiB | | |
| 192 | out of memory | 1,127 ms, 6.57 GiB | | |
| 256 | out of memory | **1,507 ms, 8.59 GiB** | out of memory | **397–402 ms, 5.33 GiB** |
| 288 | out of memory | 1,788 ms, 9.60 GiB | | |
| 320 | out of memory | out of memory | | |

Split ranges cover the geographic and lon_bands owners (< 5% apart; memory
identical); memory is the largest peak over the ranks.

- **Chunking** costs −2…+5% time and raises the largest single-GPU hidden size
  from 112–127 to 288–319; the paper's hidden 256 fits one GTX 1080 Ti.
- **Ensemble throughput at hidden 256 on 4 GPUs:** one chunked member per GPU
  gives 2.65 members/s, every member split over 4 GPUs 2.52 members/s.
- **Latency:** splitting over 4 GPUs is 3.8× faster per forecast (0.40 vs
  1.51 s at hidden 256) and 3.3–3.4× faster than one unchunked GPU at hidden
  64 / 112.
- For inference, graph splitting is a latency tool; chunking handles memory.
- Chunking leaves node states and the edge embeddings (computed once per
  step) in memory; at 1° these are ≈ 52% of the unchunked peak.
