Why does CPU placement matter, and is fixed pinning necessary?

There are three separate decisions: Slurm reserves CPUs, a process/thread has an allowed affinity mask, and the OS schedules that thread within its mask. Our job contains one Slurm task; torchrun creates four child ranks inside it. Slurm does not automatically assign distinct CPU pairs to those children. Linux children inherit affinity across fork/exec. With a healthy shared eight-CPU mask, fixed pairs need not be required. With all four main threads restricted to the same two CPUs, unused reserved capacity cannot help them.

The requirement is sufficient effective CPU capacity. Disjoint pairs are our explicit, reproducible policy, not a mathematical requirement of GraphEFM or PhysicsNeMo. GPU kernel dispatch, packing and communication progress still need host execution even with zero DataLoader workers. Delayed ranks can make other ranks wait repeatedly during AR4 and checkpoint replay.

A version-specific NCCL lead and the missing causal test

The package archive lists nvidia-nccl-cu12==2.29.3. In the corresponding upstream initTransportsRank source, the original affinity is saved, GPU-local affinity is applied, and the exit path applies comm->cpuAffinity again instead of the saved value. That is a concrete mechanism capable of retaining a narrow mask in the executing thread. Group initialization can execute work in the caller. This matches the kind of symptom seen in 6121, but the actually loaded NCCL version and pre/post-init masks must be measured before calling it the proven cause.

Our initialization passes device_id and eagerly connects NCCL. Nils initializes without that argument and then calls a barrier. The invocation/thread path and the intersection of allocated CPUs with GPU-local CPUs may therefore matter. The 6131 allocation is entirely on CPU NUMA node 1 while the GPUs report node 0; no later automatic narrowing was observed. This is a topology-specific hypothesis, not proof that NCCL or Slurm is universally broken.

A short probe should record batch/worker masks before imports, after thread setup, after CUDA setup, after eager or lazy NCCL creation and after the first collective; also record torch.cuda.nccl.version() and per-thread masks. Run eager/lazy cases in fresh processes within the same allocation. Separately compare a shared full CPU pool with disjoint pairs under the same allocation. These tests distinguish inherited/startup narrowing, NCCL behavior and the necessity of fixed pairs.

Why does Nils not need our workaround?

His code does not contain a special CPU-affinity fix either. Both use torchrun, NCCL and one PyTorch CPU compute thread per rank. Nils records initial_affinity and cpu_affinity, but his raw metadata is not committed, so his actual allocation and masks remain unknown. A healthy inherited mask could make explicit pinning unnecessary. PhysicsNeMo does not automatically fix our host allocation: both candidates in job 6121 shared the same restricted masks.

The original global-model training enables deterministic algorithms and has no explicit per-rank CPU pinning. Our archived original-model job 5031 had a normal two-CPU mask for one GPU. Nils also differs in graph size, ownership inheritance, compact CSC layout, deterministic policy, distribution-argument checks and one-GPU reference. His requirements pin the same Torch/CUDA wheel as ours; a different loaded CUDA module alone is not evidence of a different Torch runtime. His 2.42× H64 scaling and our backend ratios answer different questions.

Does PhysicsNeMo still help when CPU placement is the same?

Yes, a small advantage is observed in all three new matched pairs. Both candidates use exactly the same CPU masks. The reported throughput gain is 3.34%, equivalent to 3.24% less step time. Its archived paired-launch bootstrap ratio interval is [1.0151, 1.1011], based on only three independent pairs.

What should be cleaned up after the reference is fixed?

  1. Centralize the workload and CPU policy; preserve the same reference configuration and recorded hashes.
  2. Keep CPU/Slurm setup in the launcher. After a same-allocation placement test, prefer one initial placement plus assertions over repeated blanket helper-thread repairs. No later repair was needed in 6131.
  3. Keep one training/timing pipeline with a selectable halo transport. The current global monkeypatch is useful for this experiment, but an explicit interface would make future maintenance clearer.
  4. Audit the duplicated distributed training flow against original GraphEFM before considering Nils's original-layer wrapper as a replacement. Model-source identity alone does not prove every distributed training detail.
  5. Separate original-reference, cached-transport and live-input experiments. Retain raw archives and compact provenance; reduce duplicate reporting, not evidence.

Next evidence, in order: retrieve Nils's initial/post-init affinity and runtime metadata; run the short eager/lazy placement probe; decide whether fixed pairs are needed; then collect matching one-/two-GPU references under the chosen policy. If the small backend difference matters, use at least four counterbalanced paired launches before making it a design decision. Change deterministic/distribution-validation policy only in separately labelled tests. Code cleanup follows this stable experiment definition; it is not itself a performance claim.
